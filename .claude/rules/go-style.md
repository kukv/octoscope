# Go の書き方

## 整形と lint

`gofumpt` と `goimports` は `golangci-lint fmt` が面倒を見る。手で整えない。
有効な linter は `.golangci.yml` にある。

## lint の抑制は最終手段

**`//nolint` は原則として書かない。** 指摘が出たら、まず**指摘が出ないコードに変える**。

順に試す。

1. **指摘のとおりに直す。** ほとんどの指摘はこれで終わる
2. **設計を変えて指摘の前提を消す。** 例えば「外部プロセスに渡す引数が可変」で
   怒られるなら、引数を型で表現して文字列の組み立てを 1 箇所に閉じ込める
3. **linter の設定を直す。** プロジェクト全体でその指摘が常に不適切なら、
   `.golangci.yml` の `exclusions` に書く。1 箇所に散らばった `//nolint` より
   意図が 1 箇所に集まる

ここまでやっても残る、**そのコード固有の理由がある場合だけ** `//nolint` を書く。
そのときは次を満たすこと。

- **linter 名を指定する。** 裸の `//nolint` は全 linter を止めるので書かない
- **なぜ安全かを書く。** 「意図的」では足りない。何が保証されているから安全なのかを書く
- **上の 1〜3 をなぜ採れなかったかを書く。** これが書けないなら、まだ手はある

新しく `//nolint` を足すときは、そのことをレビューで明示的に申告する。
既存の `//nolint` を、無関係な変更のついでに増やさない。

## 命名

- パッケージ名は短い小文字の単語 1 つ。`ghclient` ではなく `gh`
- パッケージ名を型名で繰り返さない。`gh.GHClient` ではなく `gh.Client`
- レシーバは 1〜2 文字。同じ型では常に同じ字を使う
- エクスポートするのは、パッケージの外から本当に使うものだけ

## 関数

引数を 4 つ以上並べたくなったら、構造体にまとめる。
特に同じ型の引数が並ぶとき（`add, remove []string` のような）は、
呼び出し側で順番を間違えても型検査を通ってしまう。

戻り値でエラーを返せる場所で `panic` しない。
例外は、埋め込みリソースの読み込み失敗のような**ビルド時に決まるバグ**だけ。

## コメント

**基本は書かない。** コードを読めば分かることを日本語や英語で言い直さない。
名前で説明できるならコメントではなく名前を直す。

書くのは次の場合だけ。

- **コードだけでは分からない外部の事情。** API の仕様、他のツールの挙動、
  仕様上そう書かざるを得ない理由
- **一見おかしいコードが正しい理由。** 読んだ人が「バグでは」と思って直しにくる箇所
- **エクスポートした識別子の doc コメント。** 名前から始める

良い例。`gh api` が `--repo` を受け付けないという外部の事情は、コードを読んでも分からない。

```go
// gh api substitutes {owner}/{repo} from the current directory's repo; for an
// override we build the explicit path (gh api takes no --repo).
```

コードのコメントは英語で書く。

## context

**ネットワークやプロセスを待つ処理には `context.Context` を通す。**
TUI では、利用者が別の画面に移ったり終了したりした時点で、進行中の取得は
不要になる。context が無いと、その取得は最後まで走り切ってから捨てられる。

- 取得系の関数は第一引数に `ctx context.Context` を取る
- 構造体のフィールドに持たせない
- `context.Background()` を作るのは `cmd/octoscope` と、Bubble Tea の
  `tea.Cmd` を組み立てる箇所だけ
- 画面を離れる・再取得する・終了するときは、前の context をキャンセルする

同期的な 1 回の呼び出ししかない箇所に、将来のために context だけ通しておくことはしない。
並行に走らせる、あるいは途中でやめる必要が出た時点で通す。

## 外部プロセスの実行

引数は内部で組み立てた値だけを渡す。ユーザー入力（コメント本文、検索クエリ）は
フラグの値として渡し、シェルを経由させない。`sh -c` を使わない。
