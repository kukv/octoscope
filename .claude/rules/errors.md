# エラーの設計

## 3 種類を分けて扱う

| 種類 | 例 | 扱い |
|---|---|---|
| 環境の不備 | `gh` が無い、認証していない | 対処方法を添えて、翻訳した案内を出す |
| GitHub 側の失敗 | 404、403、レート制限 | 原文をそのまま見せる |
| プログラムのバグ | カタログに無いメッセージ ID | 握りつぶさず目に見える形にする |

環境の不備だけが利用者に行動を促す。GitHub 側の失敗は原文が最も情報量が多いので翻訳しない。

## エラーを作る 3 つの道具

標準ライブラリの使い分けは決まっている。迷ったらこの表に戻る。

| したいこと | 使うもの |
|---|---|
| 固定の文言でエラーを作る | `errors.New` |
| 別のエラーに文脈を足して包む | `fmt.Errorf` の `%w` |
| 複数のエラーをまとめて返す | `errors.Join` |
| 種類を判定する | `errors.Is` |
| 中身を取り出す | `errors.As` |

**包むための関数は `errors` パッケージには無い。** `%w` を使う `fmt.Errorf` が
標準の方法で、これは「文字列整形がしたい」からではなく「包む」ためにこの形を使う。
`fmt.Errorf` を `%w` 無しで使うのは、包む相手がいないときだけ。

## センチネルエラー

利用側が種類で分岐する必要があるものだけ、パッケージ変数にする。

```go
// ErrGhNotFound is returned when the gh binary is not on PATH.
var ErrGhNotFound = errors.New("gh CLI not found; install it and run: gh auth login")
```

判定は `errors.Is`。文字列比較しない。

**分岐に使わないエラーをセンチネルにしない。** 増やす前に、これを `errors.Is` で
判定する箇所を実際に書くのかを確認する。書かないなら、その場で `fmt.Errorf` すればよい。

## 包み方

```go
return nil, fmt.Errorf("parse pr list: %w", err)
```

- 文脈は小文字で始め、末尾に句点を付けない
- `failed to` / `error while` を付けない。エラーであることは自明
- 同じ文脈を二重に足さない。`gh pr: gh pr: ...` になっていたらどこかで重複している

## 利用者に見せる文字列

画面に出すメッセージは `internal/i18n` のカタログから引く。
エラーの技術的な内容（外部コマンドの stderr、HTTP ステータス）は翻訳せず、
翻訳した前置きに続けて出す。

環境の不備を案内に差し替えるのは、**UI 側で `errors.Is` を判定して行う。**
GitHub アクセス層に i18n を入れない（`.claude/rules/architecture.md` の依存の向き）。

## エラーを無視してよい場面

無視するときは `_` に入れて、なぜ無視してよいか書く。

```go
osLocale, _ := locale.GetLocale() // an error here just means "unknown"
```

理由が書けないなら、それは無視してはいけないエラー。

## Bubble Tea の中でのエラー

`tea.Cmd` の中で起きたエラーは `panic` させず、メッセージ型に載せて `Update` に返す。

エラーの種類ごとに表示場所が違う（画面全体か、フッターの 1 行か）ため、
メッセージ型を使い回さず、表示場所ごとに分ける。
