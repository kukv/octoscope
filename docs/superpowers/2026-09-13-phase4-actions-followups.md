# Actions スライスの積み残し

Phase 4 スライス 4-4「Actions」（`docs/superpowers/plans/2026-09-13-phase4-actions-and-wiring.md`、
Task 1〜8、全部完了）で見つかったもの。**このスライスで直さなかったものは、
直さないと決めた理由も書く。**

## 実データで分かったこと（このスライスで一番重い発見）

Task 7 で `cli` バックエンドと `api` バックエンドを実際の GitHub に対して
突き合わせた。以下は推測ではなく、run のログ zip を自分でダウンロードして
展開し、`xxd` / `unzip -l` で直接確かめた結果である。

### 1. GitHub は現在、run ログの zip にステップ別エントリを入れていない

`kukv/octoscope` の run `29934018532`（2026-07-22 のもの）と `34695737662`
（2026-09-12 のもの）を、どちらも今日（2026-09-13）ダウンロードして展開した。
中身はどちらも次の形だけだった。

```
<序数>_<ジョブ名>.txt      # ジョブ全体のログ（top-level）
<ジョブ名>/system.txt      # システム情報のみ
```

`internal/gh/api/joblog.go` の `stepPattern`（`<ジョブ名>/<ステップ番号>_<ステップ名>.txt`）
に一致するエントリは、2 つの run のどちらにも 1 つも無かった。

**一方で `gh` 自身のローカルキャッシュ
（`~/.cache/gh/run-log-29934018532-1784734472.zip`、2026-07-22 付）には
ステップ別エントリが残っている。** つまり以前の GitHub はこの形で zip を
返していたが、現在は返していない、という変化が起きたと見える。

**直さなかった理由:** これは api 側のバグではない。`stepLines` / `stepPattern`
のコードは削除しない — `gh` の実装した手順としては今も正しく、この形が
将来また返ってくる可能性もあるため。ただし**現在の GitHub アーカイブに対しては
到達しない経路である**ということは記録しておく。この経路を主張しているのは
`internal/gh/api/checks_test.go` の合成 zip（`zipOf` で手作りしたエントリ）
だけで、実データでの動作は確認できていない。設計 §6 にもこの実測を追記した。

### 2. したがって `failedOnly` は現在のアーカイブに対して効かない

ステップ別エントリが無い以上、`jobLogLines` は毎回 whole-job フォールバック
（`wholeJobPattern` に一致する top-level のファイルを丸ごと読む）を踏み、
全行が `Step = "UNKNOWN STEP"` になる。`stepLines` の
`if failedOnly && !failed(...)` によるスキップは per-step エントリがある
場合にしか効かないので、`failedOnly` の値に関わらず同じ行数・同じ内容が返る。

`gh` 自身も同じ状態であることを確認した。`gh run view --job 103558786732
--log-failed` は全行に `UNKNOWN STEP` を出し、フィルタしていない。

**直さなかった理由: これは `gh` を含む上流の挙動であり、ここのバグではない。**
octoscope はそれを意図して模倣しているだけである。ただし、**失敗した
チェックのログを開く**というのは checks ログ表示のいちばんの使い道であり、
そこでステップ単位の絞り込みが今は効かないというのは軽視できない。次に
手を入れるなら、ステップ境界をジョブの `steps[].started_at` /
`completed_at`（steps API）とログ行のタイムスタンプを突き合わせて復元する、
というのが候補になる。ジョブ単位のログエンドポイント
（`actions/jobs/{id}/logs`）自体にもステップ境界は無いので、この代替なしに
ステップ単位フィルタを取り戻す道は無い。

### 3. Task 7 の実データ突き合わせの結果

`cli` と `api` は job `103558786732`（run `34695737662`）に対して、
`failedOnly` の `false` / `true` どちらでも **484 行が完全一致**した
（`Step` / `Time` / `Text` すべて）。1 回目にこの job を選んだ理由は
`internal/gh/api/checks_test.go` の実録データと同じ job だったためだが、
偶然にもこの job 名（`hidden-unicode`）自体にステップ境界を壊す不可視
Unicode 文字が仕込まれており、`cli` も `api` もこの job では per-step 経路に
入れず、両方とも whole-job フォールバックに落ちていた。**つまり 1 回目の
一致は「フォールバック経路が一致した」ことの確認にとどまり、per-step 経路が
実データで一致するかは確かめられていなかった。**

そこで 2 回目、job `88970766114`（run `29934018532`、job 名 `sca`、
プレーン ASCII、6 ステップ）で再実施したところ、**251 行全部が食い違った**。
`cli` は 6 つの実ステップ名に正しく分かれ `failedOnly` で 28 行まで絞れたのに
対し、`api` は per-step エントリの無い zip しか受け取れず、全 251 行が
`UNKNOWN STEP` のまま `failedOnly` も効かなかった。

**この食い違いの原因を突き止めたところ、`cli` がステップ名を出せていたのは
`gh` の何らかの別手段ではなく、古いローカルキャッシュを読んでいたためだった。**
`~/.cache/gh/run-log-29934018532-1784734472.zip` は 2026-07-22（GitHub がまだ
per-step エントリ入りの zip を返していた頃）にダウンロードされたもので、
`sca/1_Set up job.txt` や `sca/2_Pull ghcr.io_...txt` のような per-step エントリを
今も持っている。`GH_DEBUG=api gh run view --job 88970766114 --log` を実行して
確かめると、`gh` はジョブ・run・workflow への問い合わせは出すが、**`/logs`
エンドポイントへのリクエストを一度も出していない**。つまり `gh` はこの
古いキャッシュを再検証も再ダウンロードもせずにそのまま使っていた。`api` は
キャッシュを持たないため、当日 (2026-09-13) の最新アーカイブをそのまま取得し、
そこには per-step エントリが無かった。**2 回目の比較は同じデータに対する
`cli` と `api` の突き合わせではなく、7 月のアーカイブと 9 月のアーカイブを
比べていたに過ぎない。** 同じデータ（1 回目、484 行）では両者は一致している。

**したがって、per-step 経路そのものは `cli` と `api` の間で実データによる
突き合わせが一度も成立していない。** 1 回目はフォールバック経路の一致を
確認しただけで、2 回目は異なる時期のアーカイブを比べただけである。現在の
GitHub が per-step エントリ入りのアーカイブを返さない以上、この比較を
本当の意味で実施する対象自体が存在しない。

**直さなかった理由:** api 側の実装に誤りは無く、実際に届くアーカイブの形が
そうなっている。現在のアーカイブに per-step エントリが無く、`cli` と `api` を
同じデータで比較する対象そのものが存在しないため、これ以上突き合わせを
進める術が無い。GitHub が per-step エントリ入りのアーカイブを再び返すように
なったときに、あらためて突き合わせる。

## 繰り越し（このスライスで直さなかったもの）

- **zip のキャッシュを持たない。** 同じジョブのログを開き直すたびに run の
  ログ zip を取り直す。`gh` はディスクにキャッシュする
  （`~/.cache/gh/run-log-<id>-<時刻>.zip`）。**直さなかった理由:** octoscope が
  同じログを繰り返し開く道具になったら見直す。キャッシュの寿命と置き場所という
  新しい決め事が要る。
- **run のログ zip は 1 ジョブ分を読むために run 全体を落とす。** ジョブが
  多い run では無駄が大きい。`actions/jobs/{id}/logs` はステップの境界を
  持たないので、ステップ名を捨てる覚悟が要る取り替えである。**直さなかった
  理由:** 上の実測で per-step 経路そのものが現在の GitHub に対して到達しない
  ことが分かった以上、この無駄を今削っても得るものが小さい。ステップ境界の
  復元方法を決めるときに一緒に見直す。
- **タイムアウトは本文のダウンロードを縛らない。** `internal/gh/api/api.go`
  の `responseTimeout`（16 秒）は `DialContext` / `TLSHandshakeTimeout` /
  `ResponseHeaderTimeout` にしか掛かる（`api.go:81-83`）。ログ zip を落とす
  途中で回線が細くなっても待ち続ける。値の根拠は Phase 4 設計 §2 の実測
  （30 alias で 8.13 秒、切り上げて 16 秒）。**直さなかった理由:**
  `http.Client.Timeout` にすると本文のダウンロードまで縛ってしまい、run の
  ログ zip が大きいときに途中で切れる恐れがあるため、あえて選ばなかった
  （計画の「利用者が決めたこと」2 番）。
- **`cli` バックエンドには依然タイムアウトが無い**（`internal/gh/cli/cli.go:103`
  は `exec.CommandContext` に呼び出し側の ctx を渡すだけ）。`api` だけに
  入れたので 2 つの挙動が揃っていない。**直さなかった理由:** `api` の
  タイムアウトは「`cli` と揃える」ためのものではなく `api` だけが持つ安全策
  として入れた（計画に明記）。揃えるなら `cli` 側にも同じ値のデッドラインが
  要るが、`gh` サブプロセス自体のハングを想定した設計判断が別途要る。
- **`ResponseHeaderTimeout` は `/logs` にも掛かる。** GitHub は zip を組んでから
  302 を返すので、ジョブの多い run で応答開始までどれだけ掛かるかは未計測。
  16 秒で足りるかは 4-5 の手動確認で分かる。**直さなかった理由:** TTY と
  実在の大きな run が要り、この環境では代行できない。
- **トークンが設定されているが無効なとき、`api` バックエンドでも TUI は起動し、
  実行時の `error.unauthenticated` が `Run: gh auth login` と出る。**
  `chooseBackend`（`cmd/octoscope/backend.go`）はトークンの有無しか見ておらず、
  有効性を起動時に検証していない。`gh` が入っていない機械ではこの案内は誤り。
  **直さなかった理由:** 文言をバックエンドで分けるか両方を並べるかは 4-5 で
  決める、と計画に明記済み。このスライスの範囲は `chooseBackend` の配線までで、
  エラーメッセージの文言そのものの見直しは含まない。
- **UTF-16 切り詰め（`logFileName`）はサロゲートペアの途中で切れうる。**
  45 個の絵文字 + 1 文字という入力で再現し、切れた末尾が U+FFFD になることを
  確認した。`gh` 自身がこの境界でどう振る舞うかは未確認。**直さなかった理由:**
  `gh` の `truncateAsUTF16` も同じ素朴な `[]uint16` スライスであり、こちらだけを
  直しても `gh` との整合は取れない。実害（ファイル名が 1 文字分ずれる程度）も
  小さい。
- **`readEntry` / `stepLines` の 1 分岐が raw error を `fmt.Errorf` の文脈無しで
  返している**（`internal/gh/api/joblog.go`）。**直さなかった理由:** 実害が無く
  （呼び出し元は理由に関わらず同じ扱いをする）、このスライスのスコープ
  （`gh` と同じ zip 方式を実装する）を超える。
- **run のログアーカイブを丸ごとメモリに載せており、大きさの上限が無い**
  （`internal/gh/api/joblog.go` の `jobLogLines` と `internal/gh/api/rest.go` の
  `send`）。`io.ReadAll` で zip 全体を 1 本の `[]byte` にし、そこから各エントリを
  さらに全展開するので、圧縮アーカイブ・展開後のエントリ・`[]gh.LogLine` が
  同時に常駐する。`walkPages` の `maxPages` に相当する歯止めはこの経路に無い。
  `gh` は zip をキャッシュ**ファイル**に書くのでメモリには載らない。
  **直さなかった理由: 機構は確実だが規模が未計測である。** 手元に大きい
  matrix run が無く、「何 MB になるのか」を言える数字を持っていない。
  根拠の無い数字で上限を決めるのは避ける（`.claude/rules/` の測って正当化する
  原則）。加えて `zip.NewReader` は `io.ReaderAt` を要求するため、素朴な
  ストリーミングへの差し替えはできない — `gh` の答えは一時ファイルであり、
  それを採ると「キャッシュを持たない」という上の判断とまとめて考え直すことに
  なる。**次に着手するなら、まず実在の大きい run のアーカイブサイズを測る。**
- **コンパイラによるパリティ検査は、`main.go` が 2 つの具体型を
  `usecase.New` に渡していることに依存している**（`cmd/octoscope/main.go`）。
  `parity_test.go` を消せたのは、`*cli.Client` と `*api.Client` の**両方**が
  `usecase.New` に渡る分岐がそこにあるからである。**`chooseBackend` を
  interface 1 つを返す形に畳むと、どちらか片方のパリティ検査が黙って消える。**
  直す対象ではなく、壊さないために書き残す。
- **ラベルの順序 / `parseRemote` の明示ポート / ラベル・担当者編集の部分適用 /
  `nextLink` の `,`** は 4-3 から引き続き繰り越し。詳細は
  `docs/superpowers/2026-09-13-phase4-rest-backend-followups.md` を参照。

## 実端末での確認の依頼

TTY と実在のリポジトリが要るためこの環境では代行できない。完了条件 10
（`gh` を PATH から外し `GH_TOKEN` だけで全機能が動く）は 4-5 の担当。

このスライスに固有で確認してほしいもの:

- ワークフローの再実行（`RerunWorkflow`、`RerunFailed` / `RerunAll` の両方）が
  実際の GitHub に対して動くこと。
- 失敗した run のログ表示が、大きい run（ジョブ数・行数の多いもの）でも
  16 秒のタイムアウト内に収まること。収まらない run があれば `responseTimeout`
  の値を見直す材料になる。
- トークンが無効な状態で `api` バックエンドを起動し、`error.unauthenticated`
  の文言が実際にどう見えるか（上の繰り越し参照）。
