# Repos サイドバースライスの積み残し

Repos サイドバー本体を入れたスライス（Phase 4 スライス 2-2、Task 1〜8）の
レビューで見つかったが、そのスライスでは直さなかったもの。**直さないと決めた
理由も書く。**

## 実端末での確認の依頼

このプロジェクトの規約は「TUI の変更は、テストが通っただけで完了とみなさない。
実際に起動して見る」である。設定ファイルのスライスでも同じ受け渡しをしている
（`2026-09-08-phase4-config-followups.md` の「実端末での確認」節）。今回も
TTY の無い環境では代行できないため、利用者に見てほしいものを列挙する。

- サイドバー付きの Repos タブ（120 桁以上）
- `--lang ja` での 80 桁（サイドバーが畳まれ、キーバーが 1 行に収まること）
- `h` / `l` でのペイン移動、`j` / `k` でのカーソル移動
- マウスでのサイドバー行の選択とホイール
- 設定ファイルが空でカレントもリポジトリでないときの `repos.none`

なお Task 5 の実装者が tmux で実 `gh` 認証に対して一度動かしており、サイドバーの
カーソル移動でヘッダと右ペインが切り替わることを確認している（その最中に
GitHub の 502 が 2 回あった）。ただしこれは実装者自身の動作確認であり、
**利用者自身の端末での確認の代わりにはならない。**

## 見つかったが直さなかったこと（理由つき、7 件）

### 1. `Options{}`（カレントのリポジトリ未確定）状態のタブ行を録った golden が無い

仕様（Repos タブが常にある）は `internal/tui/app/app_test.go` の
`TestReposTabExistsWithoutACurrentRepository`（`content()` ベース）で守られているが、
タブ行のレイアウト崩れは golden でしか捕まらない。

**直さなかった理由:** `content()` ベースのテストは「タブが存在すること」までは
守っており、このスライスの完了条件（設計 §11 の 1）はそこまでしか要求していない。
golden を足すかどうかは次のスライスでレイアウトが動くタイミングでまとめて判断する。

### 2. サイドバー幅を超える長いリポジトリ名を直接検証するテストが無い

fixture がすべて短い名前で、長い名前を切り詰める・折り返すケースを直接踏んでいない。

**直さなかった理由:** 挙動は `pad()` の既存仕様と一貫しており、このスライスで
新しく壊れたものではない。長い名前専用の fixture を足すのは、サイドバーの
表示ロジック自体を触るときにまとめてやる方が筋が良い。

### 3. `TestCountsMatchByPositionAndTakeTheResolvedName` が 1 行しか使っていない

「大文字小文字を区別する名前マッチ」は排除できているが、「大文字小文字を無視する
名前マッチ」まで排除できていない。

**直さなかった理由:** 実装は素直に index ベース（`RepoCounts` が返す `[]gh.RepoCount`
の並び順を信用する）で、大文字小文字を意識した分岐が実装側に無い。テストを厚くしても
守るものが増えない。

### 4. ルール桁（`x == sidebarWidth`）のクリックが表の行選択として扱われる

`internal/tui/repo/mouse.go` の境界判定で、区切り線ちょうどの列をクリックすると
行選択として扱われる。

**直さなかった理由:** このスライス以前からの既存挙動の延長であり、新規の退行ではない。

### 5. `Refresh()` / `showTab()` は行が無くても `loading` を立てて `fetchList(..., "")` を呼ぶ

`New` / `Init` だけ行の有無をガードしているのは一貫性を欠く。

**直さなかった理由:** 実害は無い。`fetchList("")` の結果は `errMsg` として返り、
`loading` を戻すだけで表示が崩れることはない。一貫性の問題であって振る舞いの
バグではないため、行を触るタイミングでまとめて直す。

### 6. 起動直後のちらつき

`app.repoResolved` は `msg.name == ""`（カレントディレクトリがリポジトリかどうか
まだ確定していない）を `repo.Model` に伝えない。そのため行が無い状態が
「確定的に空」なのか「カレントの検索中」なのか区別できず、`repos.none` が
一瞬出てから選択済みの行に切り替わることが理論上あり得る。

**直さなかった理由:** app 層（`internal/tui/app`）の変更が要り、Repos サイドバー
本体のスライスの範囲を超える。実害は表示が一瞬入れ替わる程度で、機能は壊れない。

### 7. `RepoCounts` が丸ごと失敗したとき、バッジが「—」になるだけで理由が画面に出ない

トークン切れやレート制限で GraphQL 全体が失敗すると、各行の件数バッジは
「引けなかった行」と同じ「—」表示になり、一覧そのものは動く。ただし
「なぜ引けなかったか」（認証切れなのかレート制限なのか一時的なエラーなのか）は
画面のどこにも出ない。

**直さなかった理由:** 一覧そのものは動くので 2-2 では受け入れた。理由の表示は
警告文言・表示領域の設計が要り、単独のスライスとして切り出すべき変更である。

## 2-3 に渡すもの

- 追加ダイアログ（`a`）
- 削除（`x`）
- 初回投入の導線
- `config.Save`（設定ファイルへの書き戻し）
- **一時行（設定ファイルに無いカレントのリポジトリ）は `Save` の対象外**であること。
  `internal/tui/repo/rows.go` の `row.temporary` がその印であり、保存時はこのフラグが
  立っている行を除外する
