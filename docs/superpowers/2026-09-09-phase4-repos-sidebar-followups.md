# Repos サイドバースライスの積み残し

Repos サイドバー本体を入れたスライス（Phase 4 スライス 2-2、Task 1〜8）の
レビューで見つかったが、そのスライスでは直さなかったもの。**直さないと決めた
理由も書く。**

この文書は最終の全ブランチレビュー（Critical 2 件・Important 3 件・Minor 2 件、
タスク別レビューでは 1 コミットずつしか見ないので捕まらなかったもの）で見つかった
指摘を受けて、2026-09-09 に書き直した。Critical と Important の指摘そのものは直したので
下の一覧からは消えている。この書き直しで変わった点は各項目に注記した。

## 実端末での確認の依頼

このプロジェクトの規約は「TUI の変更は、テストが通っただけで完了とみなさない。
実際に起動して見る」である。設定ファイルのスライスでも同じ受け渡しをしている
（`2026-09-08-phase4-config-followups.md` の「実端末での確認」節）。今回も
TTY の無い環境では代行できないため、利用者に見てほしいものを列挙する。

- サイドバー付きの Repos タブ（120 桁以上）
- `--lang ja` での 80 桁（サイドバーが畳まれ、キーバーが 1 行に収まること）
- `h` / `l` でのペイン移動、`j` / `k` でのカーソル移動
- マウスでのサイドバー行の選択とホイール
- 設定ファイルが空でカレントもリポジトリでないときの `repos.none`

なお Task 5 の実装者が tmux で実 `gh` 認証に対して一度動かしており、サイドバーの
カーソル移動でヘッダと右ペインが切り替わることを確認している（その最中に
GitHub の 502 が 2 回あった）。ただしこれは実装者自身の動作確認であり、
**利用者自身の端末での確認の代わりにはならない。**

## 見つかったが直さなかったこと（理由つき、8 件）

### 1. `Options{}`（カレントのリポジトリ未確定）状態のタブ行を録った golden が無い

仕様（Repos タブが常にある）は `internal/tui/app/app_test.go` の
`TestReposTabExistsWithoutACurrentRepository`（`content()` ベース）で守られているが、
タブ行のレイアウト崩れは golden でしか捕まらない。

**直さなかった理由:** `content()` ベースのテストは「タブが存在すること」までは
守っており、このスライスの完了条件（設計 §11 の 1）はそこまでしか要求していない。
golden を足すかどうかは次のスライスでレイアウトが動くタイミングでまとめて判断する。

### 2. サイドバー幅を超える長いリポジトリ名を直接検証するテストが無い

fixture がすべて短い名前で、長い名前を切り詰める・折り返すケースを直接踏んでいない。

**直さなかった理由:** 挙動は `pad()` の既存仕様と一貫しており、このスライスで
新しく壊れたものではない。長い名前専用の fixture を足すのは、サイドバーの
表示ロジック自体を触るときにまとめてやる方が筋が良い。

### 3. `TestCountsMatchByPositionAndTakeTheResolvedName` が 1 行しか使っていない

「大文字小文字を区別する名前マッチ」は排除できているが、「大文字小文字を無視する
名前マッチ」まで排除できていない。

**直さなかった理由:** 実装は素直に index ベース（`RepoCounts` が返す `[]gh.RepoCount`
の並び順を信用する）で、大文字小文字を意識した分岐が実装側に無い。テストを厚くしても
守るものが増えない。

**2026-09-09 の再評価:** 全ブランチレビューの I1 で、`prListMsg` / `issueListMsg` /
`errMsg` の「古い fetch を捨てる」判定を名前の完全一致から世代カウンタ（`Model.gen`）に
差し替えた。前提だった「大文字小文字を意識した分岐が実装側に無い」は変わっていない
（`repoCountsMsg` の受け口は今も index ベースのまま）ので、この項目の判断は変わらない。

### 4. ルール桁（`x == sidebarWidth`）のクリックが表の行選択として扱われる

`internal/tui/repo/mouse.go` の境界判定で、区切り線ちょうどの列をクリックすると
行選択として扱われる。

**直さなかった理由:** サイドバーとその区切り線はこのスライスで初めて生まれたもので、
「以前からの既存挙動の延長」という理由づけは成り立たない。実際の理由は、
影響が区切り線という 1 桁だけの当たり判定のずれに留まり、押し間違えても選択が
表の先頭行に寄るだけで、データが壊れたり別の操作に化けたりしないこと。境界判定を
やり直すのは行選択の当たり判定全体を触るときにまとめる方が筋が良い。

### 5. 起動直後のちらつき

`app.repoResolved` は `msg.name == ""`（カレントディレクトリがリポジトリかどうか
まだ確定していない）を `repo.Model` に伝えない。そのため行が無い状態が
「確定的に空」なのか「カレントの検索中」なのか区別できない。

**直さなかった理由:** app 層（`internal/tui/app`）の変更が要り、Repos サイドバー
本体のスライスの範囲を超える。

**2026-09-09 の再評価:** 「一瞬」「理論上あり得る」は過小評価だった。設定ファイルが
空（`Repositories` が無く `--repo` も無い）なら、`repos.none` は「一瞬」ではなく
**ルックアップが確定するまでの全期間**、確定的に出続ける。`resolveRepo` の上限は
`repoLookupTimeout`（20 秒）で、cold のときは実測で 6 秒を超える
（`internal/tui/app/app.go` の `repoLookupTimeout` のコメント）。この間ずっと
「本当に空」なのか「まだ調べている」のか利用者には区別がつかない。次のスライスで
優先度を上げて扱うべき。

### 6. `RepoCounts` が丸ごと失敗したとき、バッジが「—」になるだけで理由が画面に出ない

トークン切れやレート制限で GraphQL 全体が失敗すると、各行の件数バッジは
「引けなかった行」と同じ「—」表示になり、一覧そのものは動く。ただし
「なぜ引けなかったか」（認証切れなのかレート制限なのか一時的なエラーなのか）は
画面のどこにも出ない。

**直さなかった理由:** 一覧そのものは動くので 2-2 では受け入れた。理由の表示は
警告文言・表示領域の設計が要り、単独のスライスとして切り出すべき変更である。

**2026-09-09 の再評価:** C2（`SetCurrent` が counts を引き直さなかった不具合）を
直す前は、「一度も引けていない」と「引こうとして失敗した」がどちらも同じ「—」表示に
潰れていた。C2 を直した今は、`RepoCounts` を実際に呼んだ上での失敗（この項目が指す
ケース）と、そもそも呼んでいない状態は区別できるようになっているはずだが、
そのことを検証するテストはまだ無い。この項目自体（失敗理由が画面に出ない）の
判断は変わらないが、次にここへ手を入れるときは C2 後の挙動を前提に見直すこと。

### 7. サイドバーの連打が行数ぶんの `gh` サブプロセスを起こす

`internal/tui/repo/repo.go` の `selectRow` は 1 行動くごとに `fetchList` を返し、
`fetchList` は `context.Background()` で `gh pr list` を起動する。キャンセルも
間引きも無い。50 件のサイドバーを `j` で端から端まで流すと 50 個の `gh` が
並行して立つ。ホイールも同じ。

**直さなかった理由:** 出力が壊れるバグではなく資源の問題で、直すには間引きか
キャンセルかの設計判断が要る。全ブランチレビューの I1/I2 対応で `Model` に
世代カウンタ（`gen`）が入り、古い fetch の答えを世代で捨てられるようになったので、
`context.WithCancel` をこの世代に紐づけて前の fetch を止める土台はできた。
次スライスで判断する。

### 8. サイドバーが畳まれていても `h/l:ペイン` がキーバーに出る

`internal/tui/repo/render.go`（キーバーを組み立てる箇所）は状態を見ずに
ペイン移動のヒントを出す。80 桁のとき、あるいは行が 0 件でサイドバーが
そもそも無いときも `h` を押せるかのような案内が残る
（`repo_empty_ja_80.golden` の最終行に写っている）。

**直さなかった理由:** golden の再録を伴い、振る舞いのバグではない（`h` を押しても
何も起きないだけで、何かが壊れるわけではない）。`m.sidebarCols() > 0` で
出し分ければ、狭い端末やサイドバーの無い状態でキーバーに 1 枠空く。

### 9. `errMsg` が `fetchList` の失敗と `openWeb` の失敗を兼ねている

`internal/tui/repo/repo.go` の `errMsg` は、一覧の取得失敗とブラウザを開く失敗の
両方に使われ、どちらも `repo.ErrorMsg` 経由で全画面のエラー画面に飛ぶ。
`.claude/rules/errors.md` は「エラーの種類ごとに表示場所が違うため、メッセージ型を
使い回さず、表示場所ごとに分ける」と言っており、これはその原則に反している。

加えて、このスライスで入れた世代カウンタのガードは `errMsg` にも掛かるので、
`o` を押してから `OpenWeb` が返るまでの間にサイドバーのカーソルが動くと、
ブラウザを開けなかったという失敗が握りつぶされうる。

**直さなかった理由:** `errMsg` の共用はこのスライスが持ち込んだものではなく、
以前からある設計である（このスライスは世代カウンタを対称に足しただけ）。握りつぶしの窓は
`OpenWeb` が同期的なプロセス起動である以上ごく狭く、実運用で踏むことはまず無い。
分けるなら `openWeb` 専用のメッセージ型と、それをどこに描くか（全画面か、
フッターの 1 行か）の設計判断が要るので、独立した変更として扱うべきである。
