# syntax highlight の 1 行あたり固定費をどう外すか

diff 画面の 1 フレームに残った最後のコストは、`theme.Highlight` が画面に出る 1 行ごとに
払っている固定費である。これを何で外すかを決める。

## 1. 何にいくら払っているか

Apple M5 / darwin-arm64、300 ファイル × 5,000 行の PR を幅 160・高さ 40 で 1 フレーム
描いたときの内訳（`BenchmarkViewHugeDiff` = 4.93 ms、PR #104 時点）。

| 箇所 | ms/frame |
|---|---|
| `theme.Highlight`（画面に出る約 36 行） | 4.7 |
| ├ chroma の style → エスケープ列の表を組む | 2.8 |
| └ レキシング（regexp2） | 1.5 |
| `sidebarLines` ほか | 0.2 |

1 行あたりで見ると `Highlight` は約 130 マイクロ秒で、内訳は `Format` 側が約 80、
`Tokenise` 側が約 45。

### 2.8 ms の正体

chroma の `indexedTTYFormatter.Format` は、**呼ばれるたびに**
`styleToEscapeSequence(table, style)` を実行する。これはスタイルが持つ全トークン型
（github-dark で 80 前後）について `findClosest` を前景・背景それぞれに走らせ、
`findClosest` は 256 色テーブルの map を線形走査して色距離を計算する。

つまり 1 行色付けするごとに、**その行に何が書いてあるかと無関係に**
最大 80 × 2 × 256 ≈ 4 万回の色距離計算を払っている。1 フレームで 36 行なら 36 回。
プロファイルで `maps.(*Iter).Next` が flat 20% でトップに立つのはこれである。

入力は `table`（chroma のパッケージ変数の定数）と `style`（`styles.Get` が返す登録済みの
`*chroma.Style`）だけで、どちらも呼び出しごとに変わらない。chroma が毎回作り直すのは
フォーマッタを無状態に保つ設計上の都合であって、正しさのためではない。

## 2. 制約

- **見た目を変えない。** ゴールデンテストを `-update` なしで通す
- **`.claude/rules/tui.md`:** ビューは chroma を import しない。スタイル名を持つのは theme
- **`View()` は副作用を持たない。** 同じ状態からは常に同じ文字列
- chroma の `styleToEscapeSequence` も `indexedTTYFormatter` も**非公開**。theme から
  「エスケープ列を 1 回だけ作るフォーマッタ」を差し込むことはできない

最後の点が効く。chroma の外から `Format` の中の無駄を直接取り除く方法は無い。

## 3. 検討した 3 つの案

### 案 A: 画面の行を連結して `Highlight` を 1 回だけ呼ぶ

見える行を `\n` で連結して 1 回レキシングする。`Format` も 1 回になる。

実測 4.85 ms → 2.12 ms。

**採らない。** 行をまたぐレキサ状態が変わる。diff の行は連続したソースではない
（ハンクの境目で飛ぶ、削除行と追加行が交互に来る）ので、ブロックコメントや複数行文字列が
今と違う色になる。**見た目が変わる。**

### 案 B: 行ごとの `Tokenise` は保ったまま、トークン列を連結して `Format` を 1 回にする

レキシングは今のまま 1 行ずつ行い、得られたトークン列を改行トークンでつないで
`Format` に 1 回だけ流し、出力を `\n` で割って行に戻す。
`styleToEscapeSequence` が 1 フレームに 1 回になる。

- 効果: 2.8 ms → 約 0.08 ms。フレーム全体で約 2.2 ms
- 出力は今と同じはず（レキシングが行ごとのままなので）
- **代償:** `theme.Highlight(path, code) string` を複数行 API に変え、diff の描画ループも
  「1 行ずつ色を付ける」から「見える行をまとめて色付けしてから組み立てる」に組み替える。
  `diffTextLine` がガターと本文を 1 行で作っている構造を崩す必要がある

### 案 C: `Highlight` の結果を憶える（推奨）

`(背景, パス, 行のテキスト)` から色付き文字列への対応を憶える。入力が同じなら出力は
常に同じなので、**構造的に見た目が変わらない。**

効くのは、**同じ行が何度も色付けされるから**である。

- Bubble Tea は**メッセージごとに `View()` を呼ぶ**。スピナーのコマ、マウスの移動、
  ウィンドウイベントでも 1 フレーム描き直す。画面が 1 ピクセルも変わらないフレームで、
  今は 36 行ぶんの 4.7 ms を毎回払っている
- `j` を 1 回押して 1 行スクロールすると、36 行のうち **35 行は直前と同じ**

| 場面 | 現在 | 案 C |
|---|---|---|
| 画面が変わらない再描画 | 4.7 ms | ほぼ 0 |
| 1 行スクロール | 4.7 ms | 約 0.13 ms |
| 初回表示・ファイル移動・大きなジャンプ | 4.7 ms | 4.7 ms（変わらない） |

`j` を押しっぱなしにしたときのもたつき、というのが元の訴えだったので、**直したい場面に
いちばん効くのは C である。** 案 B は初回表示も 2.2 ms に下げるが、スクロール中は
C のほうが速い（0.13 ms 対 2.2 ms）。

**採る。** 理由は 3 つ。

1. 効果が大きい場面が、実際に遅いと言われた場面と一致する
2. 公開 API を変えない。`Highlight(path, code) string` のまま、呼び出し元は 1 箇所も動かない
3. 出力が入力から決まるので、見た目が変わらないことが証明に近い形で言える。
   案 B は「変わらないはず」を検証で確かめる必要がある

同じ形のキャッシュを #103 で既に 2 つ入れている（パス → レキサ、ログ → 行）ので、
このコードベースにとって新しい概念ではない。

## 4. 案 C の設計

### 置き場所

`internal/app/presentation/tui/theme/theme.go`。`lexerCache` の隣。ビューは何も知らない。

### キー

`(isDark, path, code)` の 3 つ。

- `isDark` — 配色が変わると出力が変わる。`SetDark` は実行中に変わりうる
  （現状は起動時の 1 回だけだが、そこに依存した設計にしない）
- `path` — レキサが変わると出力が変わる
- `code` — 呼び出し元は `clip` 済みの文字列を渡すので、幅が変われば別のキーになる

`struct { dark bool; path, code string }` を map のキーにする。Go の比較可能な struct なので
そのまま使える。

### 大きさの上限

**上限を持たせる。** `lexerCache` はキーがファイルパスなので実質有界だったが、こちらは
行のテキストで、長いセッションで読んだ行の数だけ増える。

上限に達したら**丸ごと捨てて作り直す**。LRU は入れない。理由:

- スクロールで効かせたいのは「直前のフレームで見た 36 行」で、これは上限のどこにいても残る。
  捨てた直後の 1 フレームだけ 4.7 ms に戻るが、その次からまた効く
- LRU はエントリごとに双方向リストのノードを持つ。得るものに対して複雑すぎる
  （`.claude/rules` の「一度しか使わないコードに抽象化を持ち込まない」）

上限は **8192 エントリ**。1 エントリは行のテキストと色付き文字列で、色付けはエスケープ列で
3〜5 倍に膨らむので、160 桁の行なら合わせて 1 KB 弱。8192 で 8 MB 程度を見込む。
画面 36 行に対して 200 画面ぶんで、スクロールにも画面の行き来にも十分足りる。

### 同期

`sync.Map` は使わない。**`sync.RWMutex` で守る普通の map にする。**

`lexerCache` が `sync.Map` なのは、キーが増えなくなったあとはほぼ読み取りだけになるから。
こちらは読みと書きが同じ頻度で来るうえ、上限に達したときに map ごと差し替える操作がある。
`sync.Map` はその「全部捨てる」が素直に書けない。

`theme` には既に `mu` があるが、これは `isDark` / `lightDark` を守るもので、別の状態である。
混ぜない（役割の違う状態を 1 つのロックで守ると、どちらの理由で取っているのか読めなくなる）。

### 何をキャッシュしないか

`chromaStyle()` と `styles.Get` / `formatters.Get` は今のまま毎回引く。前者は 15 ns、
後者は 5 ns で、測るまでもない。

### 測り方

今のベンチだけでは足りない。`BenchmarkViewHugeDiff` は**同じフレームを繰り返し描く**ので、
案 C を入れると 2 回目以降が全部ヒットし、0.2 ms のような数字が出る。これは
「キャッシュが速い」以上のことを言っていない。

**スクロールするベンチを足す。** 1 フレームごとに `j` 相当でカーソルを 1 行進め、
36 行のうち 1 行だけが新しい状態を測る。これが「押しっぱなしにしたときの 1 フレーム」で、
直したい場面そのものである。

| ベンチ | 測るもの | 現在 | 目標 |
|---|---|---|---|
| `BenchmarkViewHugeDiff` | 変わらないフレーム | 4.93 ms | < 0.5 ms |
| `BenchmarkScrollHugeDiff`（新規） | 1 行スクロール | 約 4.93 ms | < 0.5 ms |

初回表示（キャッシュが空）は 4.7 ms のまま変わらない。**これは直さない。**
直すなら案 B だが、そのために公開 API と描画ループを組み替える価値は、
1 回だけ払う 4.7 ms に対しては無い。

## 5. この設計で残るもの

- **初回表示とファイル移動は 4.7 ms のまま。** 案 B を入れれば 2.2 ms になるが、
  上に書いた理由で採らない。将来ここが問題になったら、この文書の案 B から再検討する
- **レキシングの 1.5 ms** はキャッシュが外れたときには依然として払う。これを消すには
  chroma を使わない、あるいは行ごとのトークン列を持つ話になり、別の設計になる
