## 見つかったが直さなかったこと（理由つき）

### 1. ダイアログが画面を暗くして浮かばない

モックアップ（spec §4 が参照している Artifact）は下の画面を暗転させて中央に
モーダルを置くが、この実装は既存のポップアップ（`internal/tui/review`、
`internal/tui/merge`）と同じく画面を置き換える。

**直さなかった理由:** 合成（下の画面の上に箱を重ねる）の仕組みがこのコードベースに無く、
入れるならポップアップ 3 つ全部の描き方を変える話になる。箱の中身
（見出し・入力欄・ヒント・候補・キーバー）はモックアップどおりである。

### 2. `g:取り込み` が ja の 80 桁でキーバーから落ちる

`FitKeyBar` は末尾から落とすので、ja の 80 桁では `a:追加` と `x:削除` までしか残らない。

**直さなかった理由:** `g` が要る場面（一覧が空）では、画面の本文に
`g で自分のリポジトリから選べます` が出ている。キーバーに無くても導線は切れていない。
`d` / `s` / `o` より前に出すのは、日常的に使うキーを押しのけることになる。

### 3. 追加ダイアログが一時行の名前でプリフィルされ、続けて打つと二重になる

カレントのリポジトリ（一時行）にカーソルがあるとき `a` は入力欄をその名前で埋める。
別のリポジトリを足したい利用者は、まず消してから打つことになる。

**直さなかった理由:** 意図した挙動である（一時行を永続化する経路はこれしか無く、
そこに立っているときの `a` はほぼ常にその要求である）。ただし「打ち始めたら選択範囲を
置き換える」流儀にするかどうかは入力欄の設計判断なので、次に触るときに決める。

### 4. `errMsg` が 3 種類の失敗を兼ねるようになった

`internal/tui/repo` の `errMsg` は一覧の取得失敗とブラウザの失敗を兼ねていた
（`2026-09-09-phase4-repos-sidebar-followups.md` の 9 番）。このスライスで
**保存の失敗（`noticeSave`）が 3 つ目として乗った。**
`.claude/rules/errors.md` は「表示場所ごとにメッセージ型を分ける」と言っており、
これはその原則から遠ざかる変更である。

**直さなかった理由:** 3 つとも同じ 1 行に描かれるので、表示場所は実際に同じである。
分けるなら描き分けの設計から要る。ただし**種類が増えた分、前のスライスより急を要する**。

なお世代ガードだけは分けてある: 保存の失敗はサイドバーのカーソルと無関係なので、
`msg.kind == noticeSave` のときだけ `gen` の判定を通さない。

### 5. サイドバーの連打が行数ぶんの `gh` を起こす

前スライスの 7 番のまま。`selectRow` は 1 行動くごとに `fetchList` を返し、
キャンセルも間引きも無い。

**直さなかった理由:** このスライスは `a` / `x` / `g` を足しただけで、ここを触っていない。
`gen` に `context.WithCancel` を紐づける土台はできている。

### 6. `o` の失敗通知を消す手段が無い / `RepoCounts` の失敗理由が画面に出ない / 畳まれても `h/l` がキーバーに出る / 区切り線の当たり判定

いずれも前スライスの 2・6・8・4 番のまま。このスライスで新しく壊れたものではない。

### 7. 保存に失敗しても行は画面に残る

`SaveRepositories` が失敗しても、追加した行は画面から消さず、通知行で知らせる。
次の起動では消えている。

**直さなかった理由:** 意図した挙動である。巻き戻すと、利用者が今見ているリポジトリが
目の前で消える。通知の文言（`notice.save_failed`）がその食い違いを言っている。

### 8. 初回投入の候補に上限が無い

`SeedCandidates` は 1 オーナーあたり 100 件まで引き、Org の数だけ繰り返す。
ダイアログは全部を縦に並べるので、100 件を超えると箱が端末より高くなりうる。

**直さなかった理由:** 候補の一覧はスクロールを持っていない（検索の候補は 5 件で足りる）。
スクロールを足すのはダイアログの構造を触る変更で、Search タブの保存クエリ
ポップアップ（スライス 3）が 2 人目の利用者になった時点でまとめて決めるほうが筋が良い。

### 9. `internal/gh/cli/testdata/own_repos.json` は公開リポジトリだけを残している

`gh repo list` は private リポジトリの名前も返すので、`jq` で公開ぶんに絞って
先頭 5 件だけを録った。`README.md` にその旨を書いてある。

**直さなかった理由:** 秘密情報の除去であり、テストを通すための編集ではない
（`.claude/rules/testing.md` はこの 2 つを分けている）。private の扱いを
確かめるテストが要るなら、`isPrivate: true` のケースは手で組むのではなく
別のリポジトリで録り直すこと。

### 10. `internal/tui/repo/repo_test.go:352` の不要な `cmd()`

`2026-09-11-fetch-failures-followups.md` の 3 番のまま。このスライスは
そのテストを触っていない。
