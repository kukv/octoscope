# Repos サイドバー バックエンドの積み残し

`RepoCounts` を入れたスライス（2026-09-08、Phase 4 スライス 2-1）のレビューで
見つかったが、そのスライスでは直さなかったもの。

## 見つかったが直していないこと

### 設定ファイルに同じリポジトリ名が 2 回書かれると、サイドバーに同じ行が 2 本出る

`RepoCounts` は渡された名前をそのまま alias にするので、重複した名前は
2 つの alias として送られ、両方解決してそれぞれ数値が返る。呼び出し自体は壊れない。

**直さなかった理由:** 重複排除は `RepoCounts` の仕事ではない。設定ファイルの
読み込み側で弾くか、サイドバーの行モデルで畳むかは次のスライスが Repos の
行をどう組み立てるか次第なので、そこで決める。

### `fetchList` が選択行を渡すようになったら、fake の `repo` 引数を主張させる

`internal/tui/app` と `internal/tui/repo` の fake（`fakeSource.ListPRs` /
`ListIssues` / `scenarioSource.ListPRs` / `ListIssues`）は `repo string` 引数を
受け取るがどれも無視している。今は `internal/tui/repo/repo.go` の `fetchList` が
常に空文字を渡すので、受け取った値を主張しても意味が無く、今のままで正しい。

**このリポジトリで見つかっている「空振りテスト」7 本と同じ形になるので注意する。**
Repos サイドバーのスライスで `fetchList` が選択行のリポジトリ名を渡し始めたら、
その時点で fake に受け取った `repo` を記録させ、テストがそれを主張するよう
書き直すこと。書き落とすとテストは通り続けるが何も守らない。

### 複数リポジトリの実測が 3 件しかない

設計 `docs/superpowers/specs/2026-09-08-phase4-design.md` §2 の実測は
3 リポジトリで 1 リクエスト 6.5 秒。サイドバーに現実的に並ぶ行数（20〜50 件）での
実測はまだ無い。

**Repos サイドバーのスライスで 1 回録り、設計 §2 に数値を足すこと。** 1 リクエストで
足りるか、分割やページングが要るかはその数字で決める。
