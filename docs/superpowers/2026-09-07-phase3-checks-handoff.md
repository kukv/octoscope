# Phase 3 (checks) の受け渡し — 実端末での確認

**この環境には TTY が無いので、実端末での確認は代行できない。**
golden で確かめられるのは桁と色までである。

## 用意するもの

自分が所有する、失敗した check のある PR と、外部 CI（StatusContext）を
持つ PR。無ければ、わざと失敗するコミットを積んで作る。

## 手順

1. 起動して PR を開き、`s` で checks ビューが出ることを確かめる
2. 失敗した check にカーソルを合わせ `enter` で失敗ステップのログが出ることを確かめる
3. `L` で全体のログに切り替わることを確かめる
4. `h` / `l` でログ欄が横スクロールし、端で `l` を押すとログ欄に、
   ログ欄の左端で `h` を押すと一覧に、カーソルが戻ることを確かめる
5. `R` を押し、「失敗のみ」を選んだまま `enter` で送り、
   **GitHub の Web UI で同じ PR を開き、再実行が始まっていることを確かめる**
6. 別の失敗した check で `R` → `j` で「ワークフロー全体」に切り替えて送り、
   Web UI でワークフロー全体が再実行されていることを確かめる

## 外部 CI（StatusContext）

外部 CI（StatusContext）のある PR を開き、その check にカーソルを合わせて:

- `enter` / `L` を押し、ログが無い理由が出ることを確かめる
- `R` を押し、再実行できない理由が出ることを確かめる
- `o` で Web の該当ページが開くことを確かめる

## 幅の確認

```bash
go run ./cmd/octoscope --lang ja
```

`s` で checks ビューを開き、80 桁の端末で:

- ヘッダ、一覧、キーバーの桁がずれないこと
- 日本語のログ行（全角）を含む check で `enter` を押し、ログ欄が
  折り返さず、桁もずれないこと

## 進行中の run

進行中の（まだ完了していない）check にカーソルを合わせて `enter` を押す。
Task 4 Step 5 で実測した挙動（`docs/superpowers/specs/2026-09-07-phase3-design.md` §2、
2026-09-07 実測）は次の通り:

- `gh run view --job <id> --log-failed` / `--log` はどちらも終了コード 1 で失敗し、
  stderr は `job <id> is still in progress; logs will be available when it is complete`
- `JobLog` はこのエラーをそのまま返す
- checks ビューはログ欄にこの文言をそのまま出す（追加の分岐は無い）

実端末で、進行中の check に `enter` を押したとき、ログ欄にこの文言が
（英語のまま）そのまま出ていることを確かめる。

## この段階で分かっていること

- **外部 CI（`StatusContext`）にはログも再実行も無い。** `enter` / `L` / `R` は
  理由を出すだけで、できるのは `o` で GitHub 側のページを開くことだけ
- **更新は `r` の手動のみ。** 再実行を送っても一覧は自動では取り直さない。
  一覧に新しい状態を反映させるには `r` を押す
- **checks ビューは自分の GraphQL クエリを持つ。** Work 板が使う
  `contexts` のページングは今回直していない（下記 D1）

## 報告してほしいこと

- 桁がずれた場合、**端末の種類とフォント**、`--icons` の指定
- ログが読めない形で出た場合、**その PR と check の名前**
